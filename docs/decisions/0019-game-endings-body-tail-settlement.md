# 0019 - How a game ends: body, tail, settlement

**Status:** accepted

**Context.** Most real files that failed validation failed at the very end of a game. A player who gives up is recorded in many different ways, depending on the site and on the moment the
resignation was made: the roll with the plays done and then a `Wins N points` line; a roll with dice and nothing else; dice and a single die played; dice and moves that make no sense;
`00:` (nothing was rolled); `????`; a numbered row with nothing in it; the `Wins` line written in the place of a move, in either column. Fixing each form with its own rule (the first fix
was "a roll that is a prefix of a legal play") left the next form failing, and each rule could have hidden a real mistake. The user's observation: when the end of a game looks wrong, look ahead
to the `Wins` line, which says who won and how many points, and reconcile it with the score at the start of the next game, or with the end of the match.

**Decision.** The end of a game has three layers, and every form above is a case of the second one.

1. **Body.** All plays and cube actions up to the last roll are replayed strictly: legality, turn order, cube. Nothing is relaxed here.
2. **Tail.** The *last roll of the game*, followed only by hidden plays, may hold anything: nothing, dice only, a prefix of a legal play, moves that cannot be played, or the hidden marker.
   It is tolerated **only when the file settles the game with a `Wins` line** (no bear-off or drop ended it). It cannot decide who won: the `Wins` line does. Either player may be the roller.
   - nothing, dice only, a prefix: kept as written (information, `V-RESULT` info);
   - moves that cannot be played: dropped, the roll is kept without moves as the place where the game stopped (`V-RESULT` warning: data was lost);
   - `00:` (nothing rolled): the same as a hidden play; the `Wins` line decides who gave up;
   - empty slots after the end of the game (after a bear-off, a drop or the tail) are ignored.
   A tail roll is **not part of the identity**, exactly like a hidden play: whatever a site wrote in that last slot, the match is the same match (`contentHash` skips it). The tail is flagged
   in the replay data (`ab: 1`) so that the viewer says "the game stops there" instead of "cannot move".
3. **Settlement.** The `Wins` line (winner, points) is **machine generated by the site, so it is authoritative and is never overridden**. It is checked against the **ledger**: the score at the start of
   the next game (and "and the match" at the end of the file). Evidence: in the 27 text fixtures, 131 of 133 pairs of consecutive games agree, and the 2 that do not are in the one excerpt among them (decision 0020, which lets a start score that only moves forward
   stand as "games missing"). In a contiguous match a disagreement still means that the file was edited or cut.
   - A disagreement is an **error** (unless the start score only moves forward: an excerpt, decision 0020), reported once, on the start score of the next game, and it names the `Wins` line of the previous game.
   - A bear-off or a drop whose points differ from our reading of the moves is an **error**. When the next game's score agrees with the `Wins` line, the message says so (the file is consistent with itself,
     so a play may be missing or misread, or the rules differ), but the moves are not overridden.
   - The ledger **fills in** points only where no `Wins` line says anything (a hidden play ends the game and nothing is written): the next game's score then gives the value, if only the winner's score moved
     and it is possible (at most 3 x the cube); `V-RESULT` info.
   - An unanswered double, with the doubler named as the winner, is a drop.
   - A last game that says "and the match" when the score has not reached the match length is reported.
   - When a game cannot be replayed, the running score still follows what the file declares, so one problem is reported once and not in every later game.

**What stays an error, on purpose.** A wrong play anywhere but in the tail; a tail with no `Wins` line; a roll after the tail; a `Wins` line that the next game's score does not confirm; a winner that the
next game's score contradicts (the start score of the next game is then reported as wrong).

**Consequences.** One rule instead of one rule per site quirk, and it generalises: a new variant of "the player gave up in a strange way" is already covered if it is in the last slot and the `Wins`
line is there. The price is that a real transcription mistake in the very last roll of a resigned game is no longer reported (it is a warning when moves are dropped, but the match is accepted); the
rest of the game is still verified and the result is cross-checked with the ledger. An earlier version of this decision let the next game's score override a disagreeing `Wins` line; it was removed
because no real file needs it and it would hide edited or cut files. Two renderings of the same match share an identity only if their tails agree on whether the last roll was a
complete legal play (a complete legal last roll is content; a partial or garbled one is not). Not covered: a missing `Wins` line, a gap between two games, a match that continues after a "Wins ... and the match".

**Update (2026-10-06).** Older transcriptions add three endings, read without overriding the `Wins` line (docs/game-endings.md): the
winner's last bear-off hidden (`44: ???` under the player who wins, read as that bear-off when the roll takes off every checker left);
a `Wins` cell on the row of the last bear-off, whose column says nothing about the winner; and a last game whose points are capped at
the match length. A hidden play that does not end the game is damaged (decision 0020).
