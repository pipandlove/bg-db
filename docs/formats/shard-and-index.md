# Shard, metadata and index files (version 1.0)

What `bgdb ingest` writes into `data/` and what `bgdb build` publishes into `dist/`. These are the concrete files behind
the spec sections on storage and indexes; the logical model stays independent of them (see
[decision 0007](../decisions/0007-normalised-mat-and-sidecar.md)).

## In the repository (`data/<shard>/`, written by ingest, committed)

```
data/0001/shard.json                          { schema, id, status: open|sealed, formats, counts:{matches,games,bytes} }  (bytes = size of all files of the shard, used for sealing)
data/0001/matches/<h2>/<hash>.mat             the match in the normalised MAT profile (bgdb dialect)
data/0001/matches/<h2>/<hash>.meta.json       sidecar metadata
data/0001/attachments/<h2>/<hash>.sgf|.xg     original GNU Backgammon / eXtreme Gammon file (optional)

data/enrichments/<shard>/<h2>/<hash>.json     links, tags and attachments added later to a match (bgdb enrich, or an extra file for a duplicate)
data/enrichments/<shard>/<h2>/<hash>.sgf|.xg  the attachments of that enrichment
data/hashes/<shard>.tsv                       "<content hash>\t<id>" per match of a shard that was moved to another repository
data/erased.tsv                               "<content hash>\t<id>\t<date>\t<reason>" per match removed by bgdb erase (decision 0025); lines starting with # are comments
```

`shard.json` of a **sealed** shard also holds `integrity: {algorithm: 'sha256-tree', files, digest}`: a digest of every file of the shard (sorted lines of path and sha256), recorded when the shard is sealed (or by `bgdb verify --record`).
The build recomputes it and, if it is unchanged, trusts the shard without reading its matches.

### Enrichment record

`{schema, id, links:[...], tags:[...], attachments:[{kind, file, bytes, sha256, verified, analysis, engine}], meta?:{event?, round?, date?}, contributors:[...], updatedAt}`. Links and attachments have the same shape as in the sidecar of a match. A match has at most one attachment of each kind, counting its own.
`meta` holds corrections ([decision 0022](../decisions/0022-event-round-from-headers-and-file-names.md)): each key present replaces the value of the match (`null` = none). The overlay published by `build` carries it per match (`items[id].meta`); the site applies it to the rows of the catalog and to the match page.

`<hash>` = first 16 hex characters of the SHA-256 of the canonical content ([decision 0003](../decisions/0003-canonical-match-hash.md));
it grows by two characters if two different matches ever collide on 16. `<h2>` = its first two characters. The match id is `<shard>/<hash>`.

### `<hash>.meta.json`

| Field | Meaning |
|---|---|
| `id`, `contentHash`, `canonicalVersion` | identity (full 64-character digest for collision checks) |
| `sides[]` | `{ name, rating?, experience? }`; side 0 = left column of the source |
| `matchLength`, `rules` | `0` = money game; `rules`: `crawford`, `jacoby`, `beaver`, `cubeLimit` (null = unknown) |
| `date`, `time`, `event`, `round` | descriptive metadata, may be null |
| `result` | `{ winner, score:[a,b], finished }` |
| `games[]` | per game: `points`, `kind` (single, gammon, backgammon), `how` (bearOff, drop, resign; records written by version 0.2 may also say `forfeit`, which means resign), `cube` |
| `tags` | free labels from the `.bgdb.json` sidecar (lower-case letters, digits, `-`) |
| `remarks` | the transcriber's remarks (text lines, at most 20 of 300 characters) |
| `illegalPlays` | plays made although illegal and accepted as played: `{game, row, side, player, play}` |
| `links` | video links (of the match as it was submitted; later additions are in the enrichments): `{type:'video', provider:'youtube', id, url, time?, game?, title?}` |
| `attachments` | `{kind:'sgf'\|'xg', file, bytes, sha256, verified, analysis (true/false/null), engine}` |
| `provenance` | `originalFormat`, `dialect`, `site`, `origin` (only `"otb"`, for a match declared played over the board, whose real names are published; absent otherwise, decision 0025), `originalHash` (SHA-256 of the file as submitted), `importer {name, version}`, `contributor`, `submittedAt`, `license` |
| `warnings` | codes of validation warnings at ingestion (`V-RESULT`, ...) |

The identifier a site gave to the match (`Match ID`) is **never stored** ([decision 0010](../decisions/0010-privacy-and-anonymisation.md)).

## In the published folder (`dist/`, generated by build, never committed)

```
registry.json                                 shards with base, status, matches, manifestHash
data/<shard>/shard.json                       + summary and the pointer to the catalog
data/<shard>/manifest.json                    index files with type, version, size, SHA-256, encoding
data/<shard>/index/catalog.<h8>.json.gz       the catalog (h8 = first 8 hex of the SHA-256 of the stored bytes)
data/<shard>/matches/<h2>/<hash>.{mat,meta.json}
data/<shard>/attachments/<h2>/<hash>.{sgf,xg}
overlays/enrichments.<h8>.json.gz             the enrichments, as one overlay (only when there are some)
overlays/files/<shard>/<h2>/<hash>.{sgf,xg}   their attachments
sources.json                                  the data repositories the site reads (only with build --sources)
.nojekyll                                      empty; tells GitHub Pages to serve the files unchanged
```

`registry.json` and `shard.json` follow the spec appendices. A shard of another repository (`externalShards` in the configuration) is listed with `external: true` and an **absolute** `base`; it is not copied here. `overlays.enrichments` names the overlay file. `repository`, `defaultBranch` and `videoHosts` are copied from the configuration (the Contribute page uses them). `summary` holds `dateRange`, `matchLengths` (count per length),
`events`, the number of `players`, and `playerFilter`, a deterministic Bloom filter (10 bits per item, 5 hashes) of the
normalised player names (`normalizeName`: no accents, lower case, single spaces). `positionIndexPolicy` is `none` until the
position index exists.

### `sources.json` (the data repositories a site reads)

The site of the tools repository reads its data from a series of data repositories ([decision 0024](../decisions/0024-data-repositories.md)). `bgdb build --sources <file>`
checks the list (`checkSources` in `packages/core/src/sources.js`, the same code as the site) and publishes it next to the page:

```json
{ "schema": "1.0", "name": "BGDB", "license": "CC0-1.0",
  "sources": [
    { "name": "bgdb-data-1", "url": "https://owner.github.io/bgdb-data-1/", "repository": "owner/bgdb-data-1", "state": "archived" },
    { "name": "bgdb-data-2", "url": "https://owner.github.io/bgdb-data-2/", "repository": "owner/bgdb-data-2", "defaultBranch": "master", "state": "current" } ] }
```

Sources are listed oldest first. `url` is where the repository publishes its `registry.json`: `https://`, `http://localhost` (local tests), or a path relative to the page; it ends with `/`.
`state`: exactly one `current` (it takes the contributions, and needs its `repository`), any number of `archived` (read-only, still read) and `next` (created, not read yet).
`name` and `license` of the list replace those of the registries on the site. **Without a `sources.json`** (no `--sources`), the site reads the `registry.json` next to the page,
as a single repository does.

### Overlay of enrichments

`{schema, type:'enrichments', version:1, items:{ "<id>": {links, tags, attachments:[{kind, url, bytes, verified, analysis, engine}]} }}`, gzip-compressed, named by its hash. `url` is relative to `registry.json`; the site adds `href`, the absolute address (with several data repositories, each attachment lives next to the registry that lists it). The enrichments of one match in several repositories are merged in the order of `sources.json`: links and tags are added up, an attachment of a later repository replaces one of the same kind, a correction of event, round or date of a later repository wins. The site sets the flags of the rows (video 32, attachment 16, analysis 4)
and merges links, tags and attachments into the match page. Sealed shards and their published files are unchanged by an enrichment.

The manifest lists the **index files**. Match files are content-addressed by their own name and are not listed (a manifest with
one entry per match would not scale).

### Catalog (columnar, newest first, undated last)

```
{ schema, type:'catalog', version:3, shard, count,
  dict: { players:[names...], events:[names...], rounds:[names...], contributors:[logins...] },
  cols: { id, p0, p1, len, date, ev, rd, n, s0, s1, win, fl, by } }   one array per column, same length
```

`id` = hash (shard implied), `p0`/`p1` = index into `dict.players`, `len` = match length, `date` = `YYYY-MM-DD` or `""`,
`ev` = index into `dict.events` or `-1`, `rd` = index into `dict.rounds` or `-1` (version 2; a reader of version 1 has no rounds), `by` = index into `dict.contributors` (`provenance.contributor`) or `-1` (version 3, for the `by:` search), `n` = games, `s0`/`s1` = final score, `win` = 0, 1 or -1 (unfinished),
`fl` = bit flags: **1** a gammon or backgammon occurred, **2** the cube was used, **4** analysis available (an attached SGF that carries analysis),
**8** a game ended by resignation, **16** an original file is attached, **32** at least one video link, **64** at least one illegal play was made and is kept as played. (Bit 4 is set for an analysed SGF; an XG file's analysis status is unknown, so it only sets 16.)

### Determinism

No timestamps, sorted rows and keys, the gzip header "OS" byte fixed to 3, the same Bloom bytes for the same set of names.
Two builds of the same data are byte-identical, and a sealed shard's folder is unchanged when a later shard changes
(both are tested).

## `bgdb-json` (the replay data, derived in the browser)

The replay data is **not published**: the browser reads the `.mat`, adds the sidecar and the enrichment, and derives it with `readMatch` and `toBgdbJson` of the core library (the match page also offers it as a download). Compact and lossless for replay:

```
{ schema, id, sides, matchLength, rules, date, event, round, result, links, remarks, illegalPlays, attachments:[{kind,file,verified,analysis}],
  games: [ { index, startScore, crawford, result:{winner,points,kind,how,cube},
             actions: [ {s:side, k:'m', d:[d1,d2], m:[[from,to,hit],...]},   a roll with its play (m = [] when nothing could move)
                        {s, k:'d', c:newCubeValue}, {s, k:'t'}, {s, k:'p'} ] } ] }   double, take, pass (drop)
  (a roll action carries i:1 when it is an illegal play that was made and accepted as played)
```

Points are in the mover's own numbering (24 = back point, 25 = bar, 0 = off); `hit` is 1 when the move hit a blot.
Positions are not stored: the replay recomputes them with `@bgdb/core` (rules.js).

## The normalised `.mat` ("bgdb" dialect)

Header tags `Site "bgdb"`, `Player 1`, `Player 2`, `EventDate`, `EventTime`, `Event`, `Round`, `Variation`, `Crawford`, `Jacoby`, `Beaver`,
`CubeLimit`; then `N point match`, and for each game ` Game N` (the game's number in the source: an excerpt numbered 1, 2, 6 keeps these numbers,
which `result.partial.gaps`, `IllegalPlay` and `ResultOnly` refer to), a score line and rows `  n) <left cell>  <right cell>`.
Notation: `bar`, `off`, `13/10(2)`, `*` for hits, `Cannot Move`, `Doubles => 2`, `Takes`, `Drops`. A resignation is
written as `Resigned Game` followed by `Wins N points` in the winner's column. The right column starts at column 40, or further right
when a left cell or a name is longer. `writeMat` then `readMatch` gives the same identity, result (gaps included), illegal plays and games kept by their result (tested on every fixture): this is what `bgdb build` checks.
